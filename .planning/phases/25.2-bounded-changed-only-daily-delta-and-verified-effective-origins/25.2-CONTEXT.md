# Phase 25.2: Bounded changed-only Daily Delta and verified effective origins - Context

**Gathered:** 2026-08-25
**Status:** Ready for planning
**Source:** Urgent user direction, Phase 21/25.1 contracts, and repository audit

<domain>
## Phase Boundary

Make Daily Delta a small changed-only job instead of feeding the whole fresh
sitemap into every run. Candidate selection must remain retry-safe across raw
but unpublished observations, conditional requests must perform real validator
GETs, and link discovery must have its own exact budget. Session APIs also gain
a response-derived effective origin without rewriting the raw seed evidence.

This phase changes planning/fetch behavior and read responses. It does not run
a live crawl, mutate production data, redesign the Phase 26 sitemap report, or
infer historical evidence that was never retained. After all gates pass, the
verified app is deployed through the active-crawl-blocking app-only rollout.
</domain>

<decisions>
## Locked Decisions

### Two sitemap observation terms

- Every fresh sitemap is compared with both the newest complete fresh raw
  observation and the sitemap observation currently published in the
  materialized Current Snapshot.
- The published Current Snapshot observation is the safety term. Added or
  forward-lastmod events remain pending until that term advances.
- A newer raw observation is audit and retry provenance, not permission to
  consume an event. An untrusted Delta, or a Delta whose changed selection was
  capped/incomplete, must not advance the published sitemap safety term.
- Candidate planning stays inside the Phase 25.1 per-project planning/promotion
  lock and binds raw observation ID, published snapshot revision/content
  watermark, fresh observation time, and selection completeness in DeltaPlan.
- Missing/ambiguous published lineage fails closed. Do not fall back to wall
  clock, an arbitrary newest session, or an unpublished raw observation.

### Changed-only sitemap selection

- Sitemap event candidates are only URLs added relative to the published term
  or URLs whose valid sitemap lastmod moves strictly forward. Equal, missing,
  invalid, or backward lastmod is not a changed event.
- Compare lastmod conservatively: date/date and mixed precision use UTC calendar
  dates; datetime/datetime uses UTC instants. Preserve raw lastmod strings.
- The raw comparison labels an event as newly observed or pending unpublished;
  it never suppresses a change that is still ahead of the published term.
- All evidence-backed changed events are eligible by default; the deterministic
  rotating canary cohort is up to 50. Quiet sites therefore normally produce a
  small run, while a genuinely site-wide change may produce a large run up to
  the configurable safety ceiling. Changed and explicit problem/manual work
  precede canary fillers. Canaries exclude event URLs and rotate by a persisted
  UTC epoch and stable hash, so repeated planning in one epoch is identical.
- Persist total/selected/deferred event counts, canary count/epoch, source per
  URL, and selection-complete state. The UI must distinguish event candidates,
  pending retries, canaries, and deferral.
- Other existing candidate sources remain supported and the final global safety
  cap remains authoritative. Existing and explicit saved maximums are not
  silently lowered.

### Conditional GET is real and evidence-preserving

- When `use_conditional_requests` is enabled, load retained ETag and/or
  Last-Modified from the exact materialized Current Snapshot page and send
  `If-None-Match` and/or `If-Modified-Since` on the actual GET.
- Preserve validator bytes. Do not synthesize validators, use sitemap lastmod as
  an HTTP validator, or claim conditional behavior when no validator exists.
- A 200/other non-304 response follows the normal full parse/render/persist path.
  A 304 is durable raw response evidence but short-circuits body parsing,
  extraction, resource processing, and rendering.
- Current Snapshot promotion must not overlay a 304 placeholder or delete that
  page's existing links. Its current page and link evidence remains unchanged.

### Independent discovery budget

- `max_discovered_pages_per_run` is a distinct runtime budget, not merely
  `max_pages - seed_count`. The exact value, including zero, reaches the engine.
- Initial planned candidates never consume the discovered budget.
- Static HTML and rendered DOM discoveries share one concurrency-safe admission
  helper. Only a new URL successfully admitted to the frontier consumes one
  unit; duplicates, excluded/out-of-scope URLs, and rejected frontier inserts do
  not consume it.
- The existing depth, scope, robots, exclude, frontier, and total page guards
  remain additional bounds. Zero disables all static and rendered discovery.

### Effective origin is response-only

- Session list and detail responses expose `effective_origin` only when durable
  actual launched-request/final-response evidence proves it.
- For full crawls, launched URLs are the raw SeedURLs. For Delta, launched URLs
  come from the durable DeltaPlan. Use persisted response URL/final URL/status/
  error evidence; never use canonical, sitemap loc, HTML, DNS, config, or a
  guessed scheme/host.
- Normalize only the origin serialization (scheme, host, effective port). When
  proof is absent or conflicting, return an explicit unavailable/ambiguous
  state and no effective origin.
- `effective_origin` is response-only. Do not add a mutable session-origin
  column and do not replace, normalize away, or rewrite SeedURLs.
- ProjectPage displays effective origin as the operational origin and retains
  raw SeedURLs beside it as audit provenance. Delta metadata may repeat the
  proven origin but is not its source of truth.

### Safety, compatibility, and documentation

- Preserve Phase 21 fresh observation behavior, Phase 25 provenance, Phase 25.1
  immutable lineage/promotion ordering, authorization, raw sessions, and legacy
  settings/config decoding.
- Update `ProductFeatures.md` in the functional implementation set.
- Verification begins locally and deterministically: `httptest`, Go unit/race
  tests, ClickHouse integration fixtures, frontend tests/lint/build, and diff
  checks. Production acceptance then verifies the app health, ClickHouse
  continuity, and session API/UI without starting a crawl.
- Deployment is app-only through `deploy/restart-app-safe.sh`, never `FORCE=1`,
  and is blocked while any crawl is active. No live crawl, production preview,
  or production data repair is part of this phase.

### Claude's Discretion

- Exact internal type/helper names and UI wording.
- Whether response proof is batch-loaded in the session query or by one bounded
  enrichment query, provided list endpoints do not introduce an N+1 query.
- Neutral visual treatment inside the existing dense ProjectPage table.
</decisions>

<specifics>
## Specific Ideas

- Candidate source values should make `sitemap_added`,
  `sitemap_lastmod_forward`, `sitemap_pending_unpublished`, and
  `sitemap_canary` distinguishable in persisted Delta provenance.
- A current sitemap event seen by an untrusted raw Delta yesterday must still be
  selected today when the published Current Snapshot term has not advanced.
- A 304 fixture must prove both the outgoing validator headers and byte-for-byte
  preservation of the materialized page/link evidence after promotion.
- Run a race test where static and rendered workers discover overlapping URLs
  against budget zero, one, and N.
- An HTTP seed redirect may prove a different HTTPS effective origin while the
  original HTTP SeedURL remains visible unchanged.
</specifics>

<deferred>
## Deferred Ideas

- Phase 26 report-wide sitemap availability, lexical XML identity, and lastmod
  audit UI.
- HEAD-based preflight or a HEAD-to-GET fallback workflow; this phase uses
  conditional GET.
- Historical origin backfill, seed rewriting, canonical-origin inference, or a
  durable mutable `effective_origin` session column.
- Live crawl or production data repair.
</deferred>
