# Phase 25.2: Bounded changed-only Daily Delta and verified effective origins - Research

**Researched:** 2026-08-25
**Status:** Complete

## Research Question

What must change so Daily Delta selects a retry-safe bounded changed set, uses
real HTTP validators, enforces discovery independently under concurrency, and
reports only origins proven by durable responses?

## Current Architecture And Proven Gaps

### Candidate planning recrawls the fresh sitemap universe

`internal/server/handlers_delta.go:buildDeltaCandidatesLocked` refreshes the
sitemap and passes every fresh URL to `addSource("sitemap_fresh", ...)`. The
shared `boundDeltaCandidates` then classifies only known versus new and applies
large defaults (`max_candidates_per_run=5000`, changed/new limits 1000). It does
not compare fresh lastmod with any prior observation and has no canary cohort.

Phase 25.1 already gives planning the correct serialized lineage boundary:
`deltaPlanLineage` validates the published Current Snapshot and planning holds
`qualityPromotionLock(projectID)` across lineage plus candidate reads. The
lineage includes current materialized session, raw full source, content
watermark, quality revisions, and snapshot revision. Candidate selection should
extend that transaction instead of adding another lock.

Phase 21 stores fresh raw sitemap rows on launched Delta sessions and replaces
the materialized sitemap observation on trusted promotion. A raw Delta can exist
without being published. Therefore the newest raw observation cannot be the
sole cursor: doing so consumes an event after an untrusted/capped attempt. The
published materialized observation must be the safety cursor.

### Conditional setting is currently inert

`ProjectDeltaSettings.UseConditionalRequests` is persisted and rendered, but
there is no reference outside settings/UI. `fetcher.FetchWithContext` always
creates an unconditional GET. The page table already retains response headers,
including ETag and Last-Modified, so the exact Current Snapshot page can supply
validators without a new schema.

The parse pipeline would currently persist a minimal 304 page row. Promotion
blindly overlays all Delta pages, and `overlayDeltaLinks` deletes links for all
Delta page URLs before copying new links. A 304 would therefore replace useful
page evidence with an empty placeholder and delete its graph edges. Promotion
must explicitly exclude 304 rows from both page overlay and link replacement.

### Discovery is not independently bounded

The planner calculates `MaxPages = len(planned) + MaxDiscoveredPagesPerRun`, but
the engine has no discovered counter. Static parse workers and rendered workers
call `front.Add` independently. A small candidate shortfall, redirects, retries,
or concurrent discoveries can make the total-page approximation diverge from
the configured discovery intent. A zero discovery setting is not transported
as an explicit policy; `MaxDepth` overrides are also applied only when positive.

`frontier.Add` returns whether a URL was newly admitted and serializes its own
dedup state. A single engine admission mutex around budget check plus
`frontier.Add` can make the counter exact. Both static and rendered paths must
call the same helper; otherwise rendering can bypass the cap.

### Session origin is not represented

Session list/detail responses expose SeedURLs directly. The page table already
retains requested URL, actual final response URL, response status/error, and
redirect chain. For Delta sessions the durable launched set is
`DeltaPlan.LaunchedURLs`, while `SeedURLs` intentionally retains original
project seed provenance. This is sufficient to derive a response-only origin at
serialization time without changing `crawl_sessions` or rewriting seeds.

## Recommended Architecture

### 1. Pure dual-term sitemap selector

Create one deterministic selector over normalized sitemap identity records:

```text
inputs:
  fresh observation F
  latest complete fresh raw observation R
  published materialized observation P + snapshot revision
  changed limit, canary count, rotation epoch

event relative to P:
  URL absent in P                         -> sitemap_added
  valid F.lastmod strictly after P        -> sitemap_lastmod_forward
  otherwise                               -> unchanged

raw provenance relative to R:
  event also ahead of R                   -> newly_observed
  event not ahead of R but ahead of P     -> pending_unpublished
```

The published comparison controls selection. Raw comparison only labels retry
state. Sort event candidates by stable identity and reason, select the bounded
event prefix, then select up to 50 unchanged canaries by a stable rank over
`project_id + published_snapshot_revision + UTC rotation_epoch + identity`.
Exclude all events from canaries. Persist the exact epoch and selector revision
so Preview/Run/config are explainable.

Use a strict W3C parser shared with later Phase 26 work. Date/date and mixed
precision compare UTC dates; datetime/datetime compares UTC instants. Missing,
invalid, equal, and backward values do not create a changed event. Raw values
remain unchanged in sitemap rows.

`selection_complete` means every event ahead of P was selected after global URL
policy. It is false when an event budget or final global cap defers an event.
Only `fresh && selection_complete` may replace the published materialized
sitemap observation. A raw untrusted run cannot promote at all; a trusted but
incomplete run may update selected content but holds P, so pending events remain
visible on the next plan.

### 2. Load raw and published terms under the existing lock

Add bounded storage reads that return normalized identity plus raw lastmod and
source for:

- newest raw non-synthetic complete fresh observation for the project;
- exact materialized Current Snapshot sitemap observation named by validated
  Phase 25.1 lineage;
- exact Current Snapshot page response validators by URL.

The raw observation chooser accepts complete Phase 21 `mode=fresh` Delta
observations and the trusted raw full source as the initial fallback. It rejects
running/stopped/failed, skipped/fallback, partial/ambiguous, synthetic, or
unrelated sessions. Bind its session ID and observed time in the Delta plan.

Storage reads, selection, source reads, and Phase 25.1 lineage stay within the
same planning lock. Recheck selection/published snapshot binding during
promotion before any sitemap replacement; a changed snapshot revision returns a
typed stale-baseline error rather than publishing against mixed terms.

### 3. Conditional GET request contract

Extend the fetcher with optional request validators:

```go
type RequestValidators struct {
    ETag         string
    LastModified string
}
```

Send exact non-empty values as `If-None-Match` and `If-Modified-Since` on GET.
Never derive these from sitemap lastmod. Expose on `FetchResult` which validators
were sent for tests/audit if needed. Existing callers with nil validators keep
their behavior.

For Delta, give the engine the exact materialized baseline session ID and an
enable flag. Before a page GET, load that URL's retained validators from the
baseline. A 304 produces a minimal raw page response row and counts as a
completed launched candidate, but skips parse, extraction, resources, JS
render, and new link discovery. Snapshot overlay filters `status_code != 304` in
both page and source-link operations. Integration tests fingerprint the current
page and link rows before/after promotion.

### 4. Exact shared discovery admission

Carry an optional `MaxDiscoveredPages` value to the engine separately from
`MaxPages`; Delta always supplies it, including zero. Initial seeds use the
existing seed path and do not consume it.

Add one helper that applies scope/exclusion/depth checks, locks the discovery
budget, checks remaining capacity, calls `frontier.Add`, and increments only
when Add returns true. Static and rendered paths use it. Locking the budget
decision together with Add prevents N workers from overshooting. Keep MaxPages,
MaxDepth, frontier capacity, robots, and cancellation as secondary guards.

### 5. Response-only effective origin enrichment

Batch-load origin proof for session list/detail serialization to avoid N+1
queries. Determine launched URLs from SeedURLs for a full crawl and durable
DeltaPlan launched URLs for Delta. Match persisted requested page rows with an
actual HTTP response (`status_code > 0`, no fetch error, non-empty final response
URL or requested URL). Serialize the parsed response origin with normalized
scheme/host/default port only.

Return:

```json
{
  "effective_origin": "https://www.example.com",
  "effective_origin_state": "proven"
}
```

Return empty origin with `unavailable` when no launched response proves it and
`ambiguous` when durable launched responses prove conflicting origins. Do not
infer from canonical, sitemap, raw seed string, or project config. ProjectPage
shows effective origin and separately labels the unchanged raw seed.

## Risks And Mitigations

1. **Event consumption by raw retry:** P, not R, controls eligibility.
2. **Event consumption by cap:** materialized sitemap replacement requires
   selection completeness and exact snapshot binding.
3. **Canary preview drift:** stable UTC epoch and persisted selector revision.
4. **False change from malformed lastmod:** strict parser; invalid/missing/equal/
   backward never become change events.
5. **304 data loss:** raw 304 remains in Delta, while both current page and link
   overlay explicitly exclude it.
6. **Discovery race:** one budget+frontier admission critical section shared by
   static and rendered workers.
7. **Origin guess:** response rows only; ambiguity is explicit; seeds immutable.
8. **Phase 26 collision:** Phase 26 runs later and extends shared contracts.

## Research Conclusion

No new external dependency is needed. The repository already holds raw sitemap
lastmod, Current Snapshot lineage, HTTP response headers, redirect outcomes, and
frontier admission results. The fix is to connect those facts with explicit
dual-term selection, real conditional request transport, promotion filters,
and response-time origin enrichment while keeping every unsafe fallback typed
and fail-closed.
