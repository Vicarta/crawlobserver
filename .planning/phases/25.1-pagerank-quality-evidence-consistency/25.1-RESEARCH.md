# Phase 25.1: PageRank quality evidence consistency - Research

**Researched:** 2026-08-08
**Status:** Complete

## Proven Root Cause

The deployed `Engine.finalizeSession` writes terminal status before
`RecomputeDepths`, `ComputePageRankWithOptions`, and near-duplicate analysis.
The quality scheduler accepts terminal sessions and evaluates a missing result
without a PageRank-finalization barrier. Production logs prove the exact race:

| Evidence | Time / value |
|---|---|
| Session terminal row | completed at 10:37:13 |
| RecomputeDepths | 51 URLs at 10:37:15 |
| Quality result | evaluated 10:37:18, zero-top=20, untrusted=65 |
| ComputePageRank | 51 pages completed 10:37:19 |
| Current FINAL rows | 51 eligible, 51 positive, 0 zero |

The deployed scheduler never revisits sessions that already have a result. The
local dirty worktree contains two partial mitigations: it moves terminal write
after analytics, and adds a one-way heuristic refresh when the stored zero
count is positive and decreases. Neither is deployed, and neither creates a
durable lineage contract.

## Additional Failure Modes

1. PageRank errors are logged and terminal `completed` is still written.
2. `Engine.Done()` closes before finalization, so activity/safe-restart views
   can report no engine while derived evidence is still changing.
3. PageRank report filters (`pagerank>0` plus non-redirect) and Quality Gate
   filters (HTML-ish, including redirect/error rows) are independent SQL.
4. Quality result and findings replacement is not atomic: result insert,
   partition drop, and per-finding inserts can interleave.
5. Manual/automatic PageRank recomputations do not invalidate quality by an
   evidence revision.
6. Current Snapshot metadata stores session IDs, but not the PageRank evidence
   revision on which trust/promotion was decided.
7. Historical quality replay excluded only the evaluated session when choosing
   a baseline. Older sessions could select newer sessions, creating cyclic
   baseline-evaluation dependencies and a new revision every scheduler minute.
8. Every trusted historical full crawl could initialize Current Snapshot.
   Without a durable `(started_at, session_id)` watermark, replay moved the
   authoritative project pointer backwards even after a successful repair.

## Recommended Architecture

### Shared eligible set

Define versioned `pagerank-eligible-v1`: page type HTML, status 200-299, no
followed redirect (`final_url` empty/equal URL), and canonical empty/self/equal
URL. Noindex pages remain eligible because they can be equity sinks. Redirects,
canonical aliases, non-2xx HTML, and non-HTML are excluded. `pagerank > 0` is
never eligibility. Use this predicate in reports, evidence, zero-top, and
overlap, and prove `eligible = positive + zero` for every revision.

### PageRank evidence

Add typed PageRank evidence events. Computed attempts use UUID revisions;
legacy adoption derives deterministic identity from session, predicate and
algorithm versions, options, and a stable graph/rank fingerprint. Events carry
started/finalized/failed state, source, predecessor, graph/eligible/positive/
zero counts, query identity, timestamps, and sanitized failure. A successful
mutation stamps page revision, verifies FINAL counts and fingerprint, then
publishes ready evidence; errors publish failed evidence and return.

Legacy adoption is single-flight/CAS guarded, rejects an active PageRank
mutation, reads the fingerprint twice, and publishes only if unchanged. It is
an audited `observed_existing` observation, not recomputation or page rewrite.

### Versioned quality evaluation

Store immutable evaluations keyed by `(session_id, evaluation_revision)` and
immutable findings keyed by that revision. Publish a separate current-quality
pointer only after both are durable; prior generations are never dropped. An
identical session + evidence + rules + baseline revision produces the same
evaluation revision and POST returns the existing result.

That identity assumes evaluator semantics are named by their revision. The
immutable Delta lineage gate added one possible finding after the original v2
evaluations existed; retaining the v2 name made new findings collide with an
old immutable generation. A global v3 would also advance full-baseline current
pointers and strand Delta bindings to their exact immutable v2 baseline. The
bounded migration therefore keeps full crawls on v2 and assigns v3 only to
non-full/Delta evaluations. Old Delta v2 rows become stale history, scheduler
publishes v3 once, and valid v3 Delta binding continues to reference full v2.

Scheduler refresh is a direct revision/rules comparison. It handles
improvement, deterioration, top-order changes, restart recovery, and replay.
Quality evaluation refuses absent, failed, or changing evidence. Snapshot
metadata and append-only promotion events bind evaluation, evidence, rules,
baseline, previous pointer, and published pointer. Promotion is independently
CAS-retryable: repeated POST can reconcile promotion even when evaluation is
unchanged.

Baseline selection is lexicographically historical: candidates must be strictly
older than the evaluated session by `(started_at, session_id)`. Current Snapshot
uses an append-only authoritative promotion journal with a full-crawl source and
latest-content watermark. Full and delta writers repeat the chronology check
inside storage after server preflight; a concurrent newer publication therefore
returns `superseded` without an older copy/overlay or applied event. Repeated
scheduler passes then converge instead of cycling revisions.

Delta plans need two distinct baseline identities. The materialized Current
Snapshot/current watermark identifies the exact predecessor content and quality
revision, while the raw full-crawl source identifies the PageRank/quality
baseline retained through Delta fold. The promotion journal is the immutable
lookup for replay; consulting either session's mutable current quality pointer
would incorrectly degrade an already-applied Delta after re-evaluation.

The append-only journal does not by itself make candidate planning atomic: the
materialized snapshot is updated in place before its pointer is published. A
planner that captures journal lineage and then reads pages without the same
per-project mutation lock can pair old provenance with new content. Planning
therefore holds the promotion lock across both operations; graph-deleting admin
jobs retain it until PageRank is finalized for the same reason.

Fold retention has a separate identity boundary: the prior Delta raw session
must disappear so scheduler replay cannot treat it as active crawl input, but
the next Delta's journal revision still needs that predecessor's exact quality
evaluation/findings and PageRank attempt. Cleanup therefore prunes session and
heavy crawl payload while retaining only those immutable dependency facts.

### API and UI

- `GET /api/sessions/{id}/quality` returns evaluation/evidence provenance and a
  stale flag calculated against latest evidence.
- `POST /api/sessions/{id}/quality/re-evaluate` requires admin plus session
  access, terminal state, and no active compute. It adopts existing evidence if
  needed, evaluates synchronously, and returns `{changed, result}`.
- Quality modal shows provenance and stale state; admins get a Re-evaluate
  command with loading/error/success states.

## Safety And Scope

- No crawl, PageRank recompute, threshold change, or manual data patch is part
  of acceptance.
- The endpoint authorization audit and OpenAPI work remain Phase 27/28.
- Deployment is app-only after two no-active-crawl checks (before build/restart
  as applicable), with no FORCE and no ClickHouse restart.
- Before migration/recovery capture prior image/version, exact quality state,
  snapshot pointer/provenance, and metadata-only rollback backup. The stale
  evaluation must remain queryable after repair.
