# Phase 25.1: PageRank quality evidence consistency - Context

**Gathered:** 2026-08-08
**Status:** Ready for planning
**Source:** Production defect delegation and read-only production audit

## Phase Boundary

Correct the contradiction between Internal PageRank and Crawl Quality for the
same session. Terminal session state, PageRank reports, quality evaluation, and
Current Snapshot promotion must agree on one finalized PageRank evidence
revision. Provide deterministic repair for already-completed sessions without
a new crawl or PageRank recompute.

## Locked Decisions

### Production case

- Project Gerus, session `cecabb70-b621-48a1-9dc4-1feb3c3757cb` is the required
  acceptance fixture.
- Production persisted `completed` at 10:37:13, evaluated quality at 10:37:18
  as `untrusted · 65` with `pagerank_zero_top_pages=20`, and completed PageRank
  at 10:37:19.
- A later read-only query shows 51/51 eligible HTML pages with positive PR and
  zero eligible pages with PR zero. The quality fact is stale.
- The trusted baseline is `52d3dd2c-1396-4126-9a4f-1c2d9111926e`; the
  `crawl_config_changed` warning remains legitimate and is not suppressed.

### Required behavior

- `completed` cannot become visible before durable PageRank finalization.
- PageRank failures do not silently publish a clean completed session.
- Report counts and `pagerank_zero_top_pages` share one predicate and evidence
  revision; 51/51 with PR means the zero count is 0 for that same set.
- Quality replacement is evidence-driven in both directions, not a heuristic
  that only clears positive zero counts.
- Current Snapshot promotion requires the quality result to reference the
  latest finalized PageRank evidence.
- An admin-only POST quality re-evaluation is synchronous, idempotent for the
  same evidence/rules input, audited through durable revision fields, and read
  back by the existing GET quality endpoint. It does not launch a crawl or
  recompute PageRank.
- Quality UI displays evaluation time/revision and PageRank evidence
  revision/source/status/counts, and offers re-evaluation only to admins.

### Safety

- Never stop an active crawl, never deploy with `FORCE=1`, and restart only the
  app through `deploy/restart-app-safe.sh` after a clean safety preflight.
- Do not manually edit historical pages, sessions, PageRank values, or quality
  rows. Production repair must exercise the supported typed endpoint.
- Do not weaken `pagerank_zero_top_pages_max`, hide findings, require a new
  crawl, or treat manual PageRank recalculation/waiting as the fix.
- Preserve all unrelated dirty-worktree changes and keep Phase 26 untouched.
- Update `ProductFeatures.md` in the functional change set.

## Deferred

- Phase 27: project read-only versus work-triggering/system-wide authorization
  matrix. The Growth Core `CRAWLOBSERVER_API_KEY` is intentionally agency-wide
  and full-access; its rights do not change here.
- Phase 28: versioned OpenAPI/JSON Schema, external agent guide coverage, and
  sanitized snapshot/quality/evidence projections.
- General Current Snapshot copy-on-write redesign is outside this urgent phase;
  this phase only blocks publication/promotion on mismatched PageRank evidence.
