# Phase 25.5 Research

## Existing Authentication

- Local users currently store `username` and a bcrypt `password_hash` in
  SQLite. `POST /api/auth/login` authenticates either that hash or the configured
  server administrator password.
- Successful login creates an opaque random server-side session referenced by
  the `crawlobserver_session` HttpOnly, SameSite=Lax cookie. The current TTL is
  seven days.
- API keys and cookie sessions share the authorization middleware. Viewer
  project assignments are stored separately in `user_projects`.
- User Management creates and edits usernames/passwords. No user email,
  invitation, login challenge, mail sender, or delivery audit exists.

## Resend Contract

Official Resend documentation defines `POST https://api.resend.com/emails` with
Bearer authentication and required `from`, `to`, and `subject` fields. Direct
HTTP callers must provide a User-Agent. `Idempotency-Key` is supported for 24
hours and is bounded to 256 characters. A verified owned domain is required;
Resend recommends a transactional subdomain. Standard errors include 400, 401,
403, 429, and 5xx.

Sources:

- https://resend.com/docs/api-reference/emails/send-email
- https://resend.com/docs/api-reference/introduction
- https://resend.com/docs/dashboard/domains/introduction

## Minimal Architecture

1. Extend the existing SQLite store rather than introduce another database:
   nullable user email/verification fields, invitations, and login challenges.
2. Keep the existing opaque session table and authorization middleware; change
   only session issuance to 14 days and local identity display to email.
3. Implement a narrow sender interface beside the auth handler. Production uses
   the Resend HTTPS API; tests inject a recording fake.
4. Replace public password login with request-code and verify-code endpoints.
   Add public invitation inspection/acceptance endpoints and authenticated
   administrator invitation operations.
5. Replace the existing login and user-management controls in place. Do not add
   a second auth framework or external identity provider.

## Security Boundaries

- Non-enumeration applies to code requests: the response is independent of
  whether an account exists or delivery occurs.
- Codes and invitation tokens never appear in logs, API readbacks, or storage
  plaintext. Resend payload tests inspect only the injected fake sender.
- Codes are one-time, expire after 15 minutes, allow five failed attempts, and
  only the newest unconsumed challenge is eligible.
- Invitation tokens are high-entropy, one-time, expire after seven days, and
  replacement revokes older tokens.
- Login/invitation routes use the existing per-IP auth limiter; challenge state
  adds per-account replay and attempt protection.
- Existing cookie sessions remain valid during migration, but the password
  endpoint and configured-password local-user fallback are removed.

## Failure Semantics

- Login-code request: stable accepted response even for unknown email or
  provider error; detailed provider error is redacted and logged server-side.
- Login verification: typed invalid-or-expired response without revealing more
  account state than needed.
- Admin invitation: provider failure returns an explicit retryable error and
  leaves a pending user that can be re-invited.
- Resend timeout, non-2xx response, and malformed success body fail closed.

## Migration And Rollout Risk

Removing password login before at least one administrator accepts an invite can
lock out the UI after the last legacy session expires. The rollout must verify a
current admin session, configure Resend first, deploy without invalidating
sessions, and immediately issue/accept the administrator invite. If those
prerequisites are unavailable, implementation may be committed and pushed but
production rollout must stop rather than retain a password fallback.

## Validation Architecture

- Store tests: email uniqueness/normalization, legacy row loading, invitation
  expiry/replacement/replay, code expiry/attempts/replay, and session TTL.
- Resend client tests: request shape, bearer/User-Agent/idempotency headers,
  timeout/error redaction, and no secret leakage using `httptest.Server`.
- Server tests: public route boundary, generic request response, fake delivery,
  invite migration, cookie attributes, authorization, logout, and removal of
  password login.
- Frontend tests: email/code state machine, invitation states, migrated/new user
  administration, and absence of password controls.
- Repository gates: focused race tests, `go test ./...`, focused `go vet`,
  `go build ./...`, frontend tests/lint/build, and `git diff --check`.
- Production: two no-force active-crawl gates, app-only restart, preserved
  ClickHouse identity/health, existing admin session, invite delivery, and
  password endpoint rejection. No crawl or rescan.
