# Phase 25.5 Context

## Locked Decisions

- Replace local username/password login immediately; do not retain the old
  login endpoint or password form as a transition path.
- Migrate existing users through administrator-issued invitations while
  preserving their user IDs, roles, project assignments, active state, and any
  still-valid cookie sessions.
- An invitation is single-use and valid for seven days.
- A login code is a single-use six-digit code valid for 15 minutes.
- A successful invitation acceptance or login creates a 14-day cookie session.
- Send invitation and login emails through Resend. Credentials stay on the
  server and tests must never contact the live provider.
- Keep API keys and existing project authorization unchanged.
- Update `ProductFeatures.md` with the functional change.
- Commit and push completed work. Production deployment is app-only and must
  use the existing no-force active-crawl safety gate.

## Implementation Decisions

- Normalize email with trim and lowercase and validate it as one mailbox
  address. Enforce uniqueness with a partial SQLite index so legacy users may
  temporarily have no email during migration.
- Store random invitation tokens only as SHA-256 hashes. Resending creates a
  new invitation and revokes older outstanding invitations for that user.
- Store short login codes only as bcrypt hashes. Issuing a new challenge
  invalidates the previous one; five failed attempts invalidate the challenge.
- `POST /api/auth/code/request` always returns the same accepted response for
  unknown, inactive, unverified, and known emails. Provider failures are
  redacted in logs and are not used as an account-existence oracle.
- Invitation delivery is an authenticated administrator action and therefore
  returns a typed delivery failure that can be retried.
- Preserve current cookie storage and logout semantics. Set `HttpOnly`,
  `SameSite=Lax`, 14-day expiry, and `Secure` when `server.public_url` is HTTPS.
- Existing password hashes may remain as inert legacy columns in SQLite, but
  no endpoint, middleware fallback, or frontend control may authenticate a
  local user with them.
- Preserve currently valid local-user sessions so the signed-in administrator
  can send the first migration invitation after rollout.

## Scope Boundary

This phase establishes verified email identities and authentication delivery.
It does not send crawl, Quality, backup, or operational error notifications;
that is a separate future feature.

## Production Prerequisites

- A Resend API key restricted to sending.
- A verified Resend domain/subdomain and configured sender address.
- A correct HTTPS `server.public_url`.
- At least one still-valid administrator cookie session for issuing the first
  migration invitation, or rollback before that session expires.

## Acceptance

1. Existing admin session remains valid after schema migration.
2. Admin can assign an email and send a seven-day invite to an existing user.
3. Accepting an unexpired invite verifies the email and creates a 14-day
   session; expired, replaced, and replayed tokens fail.
4. Verified users request and consume a 15-minute code; unknown emails receive
   the same request response and no email.
5. Password login endpoint and password UI are gone.
6. API keys and role/project authorization remain unchanged.
7. Tests use a fake sender and contain no live Resend call.
